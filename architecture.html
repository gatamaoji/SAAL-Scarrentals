Version 1.0 · 3 November 2026 · Consolidated planning document. This is an architecture and schema blueprint; production deployment requires completion, testing and security review of the full application and database.

Executive summary

The proposed system is a modular Car Rental Management System (CRMS) backed by a standalone SQLite relational database file. The live SQL database is allocated a maximum capacity of 50 GB. Customer documents, photographs, generated PDFs, exports and backups are stored outside the SQL database under separately managed storage policies.

Access ruleThe application should access the database through a controlled backend service. A browser-based HTML/JavaScript front end must not open or manipulate the SQLite file directly.

1Executive recommendation

Recommended foundation: SQLite 3 as an embedded SQL engine, with the database stored as a separate file named car_rental.db. SQLite provides relational tables, SQL queries, indexes, constraints and transactions without requiring a separate database server. It is appropriate for a single-computer deployment or a small installation where all clients access one host application service.

Scale thresholdIf the business requires multiple branches or many computers writing concurrently over a network, reassess the design and consider PostgreSQL as a central database server. Do not share an active SQLite database file directly over a network drive.

4Database relationships and rental lifecycle

The same customer, vehicle and rental agreement records should remain linked through the full rental lifecycle. Avoid copying customer or vehicle master data into every transaction. Store references to the master records and preserve a snapshot of contract-specific terms, such as the agreed rate, within the agreement.

StepProcessKey records
1Register customer and verify required documentscustomers; customer_documents
2Create booking and check requested datesbookings; booking_items
3Check availability and allocate a vehiclevehicles; bookings; rental_agreements
4Generate agreement and record collection inspectionrental_agreements; vehicle_inspections; inspection_items
5Collect rental charges and depositinvoices; invoice_items; payments; deposits
6Manage rental, extension or incidentrental_extensions; accident_records; audit_logs
7Inspect returned vehicle and record new damagevehicle_inspections; vehicle_damage
8Calculate final charges, settle balance and depositinvoices; payments; refunds; additional_charges
9Release vehicle only when return checks are completevehicles; inspection records; maintenance records

Principal relationships

  • One customer can make many bookings.
  • A booking may convert into one or more rental agreements, subject to the business model.
  • A vehicle can have many rental agreements over time, but not overlapping active allocations.
  • A rental agreement can have multiple invoices, payments, inspections and charges.
  • A vehicle can have many maintenance, insurance, registration and damage records.
  • A user can create many audit-log entries.

Availability logicAvailability should be calculated from booking and agreement date ranges, vehicle status, maintenance blocks and inspection release status. A manually selected "Available" status must not override a conflicting active rental or maintenance period.

Core integrity rules

  • Vehicle registration and fleet numbers must be unique.
  • Customer numbers, booking references, agreement numbers and invoice numbers must be unique.
  • Return date/time must be later than pickup date/time.
  • Payments and monetary quantities must not be negative.
  • A vehicle cannot be allocated to overlapping rentals.
  • Vehicles under maintenance, accident hold or inspection cannot be handed over.
  • Completed agreements and financial transactions should not be permanently deleted; corrections should use authorised reversals or adjustments.
  • Expired or unverified documents should trigger an operational validation before handover.

6Financial model and calculations

The financial model should keep rental income, security deposits, refunds and other liabilities separate. A refundable security deposit is not rental revenue. Record every payment and refund as a transaction and reconcile them against invoices and deposits.

  • Daily, weekly and monthly rental rates; preserve the historical rate agreed for each contract.
  • Rental duration and pro-rata rules, including clear policies for partial days.
  • Seasonal, weekend, category-specific, corporate and negotiated rates.
  • Late-return, extra-kilometre, fuel replacement, cleaning and damage charges.

  • Invoice, receipt and credit-note generation with traceable references.

9Storage quota and monitoring architecture

The live SQL database has a maximum allocated capacity of 50,000,000,000 bytes (50 GB decimal). This is an application-enforced quota, supplemented by SQLite's page-count limit and operating-system free-space checks. It is not the same as the total disk space used by documents, WAL files, temporary files or backups.

Storage componentPolicy
Main SQL databaseMaximum 50 GB live database page allocation.
WAL/SHM and temporary filesMonitor separately; reserve adequate working disk space.
Customer documents and photosSeparate document storage quota and file-size limits.
PDF agreements and invoicesSeparate document storage; retain references/metadata in SQL.
BackupsSeparate backup capacity and retention policy.
Exports and reportsTemporary storage with retention and cleanup policy.

Suggested capacity alerts

UsageLevelAction
Below 70%NormalContinue normal monitoring.
70%WarningNotify administrator; review growth trend.
90%CriticalRestrict large imports; plan capacity action.
98%Near limitBlock nonessential writes/uploads; urgent administrator action.
At 50 GBLimit reachedReject writes that would exceed quota safely; preserve read/export and recovery functions where possible.

SQLite page-limit calculation

With a 4096-byte page size, the page count is floor(50,000,000,000 ÷ 4096) = 12,207,031 pages. That gives a maximum database size of 12,207,031 × 4096 = 49,999,998,976 bytes, which stays just under the 50 GB decimal quota. Compute and verify this integer at database initialisation.

PRAGMA page_size = 4096;
PRAGMA max_page_count = 12207031;
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
What the page limit does not coverThe page-count limit constrains database pages, not every byte associated with SQLite operation. Monitor database file size, WAL growth, temporary files and free disk space. The application should estimate the size impact of large writes and check capacity before committing. Do not promise a mathematically strict 50 GB total footprint unless the operating system also enforces a disk quota over the database working directory.

Required production additions

  • Create roles, permissions, role_permissions and staff tables before implementing user administration.
  • Add invoice_items, deposits, refunds, inspection records, inspection items, rental drivers, rental extensions, insurance, registration, accident and damage tables.
  • Add controlled status values, preferably lookup tables or CHECK constraints, and document permitted status transitions.
  • Add transactional booking allocation logic and tests for concurrent booking attempts.
  • Add indexes based on actual search and reporting patterns; avoid unnecessary indexes that increase write and storage overhead.
  • Use schema migration scripts with version tracking; do not modify production tables ad hoc.
  • Store document metadata and secure file references in SQL, not large binary files, unless there is a specific reason to use database BLOB storage.

Security controls

  • Individual user accounts; no shared logins.
  • Password hashing using a modern password-hashing algorithm; never store plain-text passwords.
  • Role-based permissions enforced by the backend service.
  • Encryption for the database at rest and for sensitive documents, with managed keys.
  • TLS for any network connections to the application service.
  • Session timeout, account lockout or throttling, and secure password reset.
  • Audit logs for create, update, approve, reverse, export and administrative actions.
  • Restrict access to identity documents and personal information; define retention and deletion policies consistent with applicable law.
  • Use parameterised SQL queries to prevent SQL injection.
  • Protect backup copies to the same standard as the live database.
SQLite has no native user accountsSQLite does not provide database user accounts or row-level security comparable to a server database. The backend application must authenticate users and enforce permissions. Anyone with direct access to an unencrypted database file may be able to read or modify its contents; operating-system permissions and encryption are therefore important.

12Backup, recovery and database maintenance

Suggested retention policy (confirm available backup capacity and business/legal requirements before adoption):

Backup typeSuggested frequency / retention

WeeklySeparate weekly backup; retain a suitable number of weeks, e.g. 8.

Operational requirements

  • Use SQLite's online backup API or another SQLite-aware method to create a consistent backup while the database is in use.
  • Do not copy only the main .db file while WAL transactions are active and assume it is a complete backup.
  • Verify backup file integrity and perform test restores.
  • Document recovery steps, backup locations, encryption keys and responsible staff.
  • Monitor disk space before backup and maintenance operations.
  • Run PRAGMA integrity_check on a schedule and investigate failures.
  • Use PRAGMA optimize as appropriate; plan VACUUM carefully because it can require additional disk space and time.
  • Use WAL checkpoint management and monitor WAL growth.

Deployment guidance

Minimum acceptance tests

  • The database initialises with the required schema and reports the configured page limit.
  • Foreign-key constraints reject invalid references.
  • Duplicate registration, customer and transaction identifiers are rejected.
  • Two simultaneous attempts to reserve the same vehicle for overlapping periods cannot both succeed.
  • Vehicles in maintenance or return-pending status cannot be handed over.
  • Payments, deposits and refunds reconcile correctly; deposits are not counted as revenue.
  • Storage warnings trigger at configured thresholds and writes are safely rejected when quota would be exceeded.
  • WAL growth, free disk space, documents and backup storage are monitored separately.
  • A backup can be restored and passes integrity checks.
  • Role permissions prevent unauthorised access to financial and personal records.
  • Audit records identify the user, action, timestamp and affected record.
  • A schema migration can be applied and rolled back or recovered using a documented procedure.

15Important technical limitations and decisions

Scope of the 50 GB limitThe 50 GB requirement is the maximum allocated size of the live SQL database pages. It does not automatically include the WAL file, shared-memory file, temporary files, external documents, exports or backups. These must have their own quotas and disk-space controls.
  • A SQLite max_page_count setting caps the number of database pages, not the entire application folder or every associated working file.
  • Use a backend quota manager and operating-system storage controls if a strict physical storage ceiling is required.
  • The example schema is a starting point, not a complete production-ready database. The full implementation needs all tables, indexes, triggers, validation and migration scripts.
  • SQLite WAL mode supports concurrent readers but still has a single writer at a time. It is not a substitute for a server database in a high-concurrency, multi-branch environment.
  • Encryption is not built into standard SQLite by default; choose and test an appropriate encrypted database solution or storage encryption strategy.
  • Backup retention must be sized separately. A 50 GB database can require substantially more than 50 GB of backup space.
  • Before collecting customer identity documents, define lawful purposes, access restrictions, retention periods and secure disposal procedures.
Final design decisionBuild the first version with SQLite 3, a standalone car_rental.db file, a 50 GB live database page quota, a separate document repository, a backend service, role-based application security, audit logging and verified off-device backups. Keep the relational schema modular so the business can migrate to PostgreSQL if its scale or concurrent workload grows.
